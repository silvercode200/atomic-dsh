# dsh-fake-llm — фиктивная локальная LLM для dsh

HTTP-сервер на чистом Node >= 22 (ESM, ноль зависимостей), который dsh принимает
за настоящую модель: говорит по протоколу `anthropic-messages` (POST `/v1/messages`),
стримит SSE-события, эмулирует tool_use-циклы и отчитывает usage. TUI dsh полностью
оживает — стрим, thinking, тулз-карты, tps, ctx-бар, comp-поле — но ни один реальный
токен не тратится. Плюс реплей-мост: лог реальной сессии dsh конвертируется
в сценарий с таймингами записи — единственный способ ловить на стенде
таймингово-зависимые визуальные баги (см. «Реплей реальных сессий»).

Протокол выверен по фактическому потребителю: `@deepseek-ai/dsh-llm-pi-ai` поверх
`@earendil-works/pi-ai` и официального `@anthropic-ai/sdk` (клиент всегда шлёт
`stream: true`, путь запроса — `{baseURL}/v1/messages`).

## Запуск

```bash
node tools/dsh-fake-llm/server.mjs
# проверка:
curl -s http://127.0.0.1:8787/health
# {"ok":true,"uptime_s":3,"sessions":0,"scenarios":["ctx90","long","short","subagent","tools","waves"]}
```

## Подключение к dsh

1. Запустить сервер (см. выше).

2. Задать фиктивный ключ (pi-ai требует непустой apiKey для anthropic-messages
   даже у локального сервера без авторизации; значение — любая строка):

   ```bash
   export FAKE_LLM_KEY=fake-local-key
   ```

3. Добавить роут в `~/.dsh/settings.yaml` в существующую секцию `llm-pi-ai.providers`
   (существующие роуты `bg`/`cli` не трогать; никаких реальных ключей здесь нет —
   только ссылка на env-переменную):

   ```yaml
   llm-pi-ai:
     providers:
       fake:
         displayName: Fake LLM (local)
         api: anthropic-messages
         apiKeyEnv: FAKE_LLM_KEY
         baseURL: http://127.0.0.1:8787
         models:
           - id: fake-sonnet
             name: Fake Sonnet (local)
             contextWindow: 262144
             maxTokens: 32768
   ```

   `contextWindow: 262144` важен: от него dsh считает заполнение ctx-бара, на которое
   рассчитан сценарий `ctx90`.

4. Перезапустить dsh, выбрать провайдер `fake` и модель `fake-sonnet`. Дальше —
   обычный диалог: сценарий выбирается содержимым сообщения (см. ниже).

## Сценарии и выбор

Сценарий выбирается по последнему тексту пользователя:

- **маркер** `SCENARIO:<name>` — детерминированный выбор, например
  `SCENARIO:tools запусти цикл инструментов`;
- иначе **ключевые слова** (эвристика): `ctx90` (`ctx 90`, `90%`), `subagent`
  (`субагент`, `subagent`), `long` (`длинн…`, `long`), `tools` (`тулзы`,
  `инструмент…`, `tools`, `bash`);
- иначе — `short` (сценарий по умолчанию).

Маркер сбрасывает состояние диалога на выбранный сценарий с нуля.

| Сценарий    | Что делает                                                                 |
|-------------|----------------------------------------------------------------------------|
| `short`     | короткое thinking + короткий текст (ответ по умолчанию)                     |
| `long`      | длинная генерация: циклит пул абзацев до истечения `STREAM_TOTAL_MS` (2-5 мин) |
| `tools`     | цикл 3 tool_use: `Bash ls` -> `Read file` -> `Write file`, затем финальный текст |
| `subagent`  | текст с явной структурой сабагент-волн (ВОЛНА 1/2/3, SUMMARY/FILES/FULL_LOG) |
| `ctx90`     | usage, заполняющий контекст до ~90% окна 262144 (235930 входных токенов)     |
| `waves`     | реальный спавн субагента: `tool_use subagent` (run_in_background:false) -> dsh запускает НАСТОЯЩЕГО субагента, после tool_result финальный текст |

## Сценарий waves — живые карточки субагентов (D7)

`subagent.json` — только текстовая эмуляция волн; `waves` делает реальный спавн.
Механика: сервер эмитит `tool_use` c `name="subagent"` и input-схемой тулзы
dsh (`{description, prompt, run_in_background:false}`) — dsh запускает
настоящего субагента, тот делает свой model-call (его промпт НЕ содержит
маркер `SCENARIO:`, другая сессия → сервер отдаёт дефолтный `short`),
возвращает результат, родитель получает `tool_result` и доигрывает хвостовой
текст. В TUI по-настоящему рендерятся:

- заголовок карточки `Subagent: <описание> · <модель> · <длит> · <N tok> ·
  <N tools> · <статус>` (`SubagentMessage`);
- waterfall активности во время выполнения (макс 3 строки `  │ …` или
  живые строки вывода) и свёртывание после settled;
- смена статуса `running` → `completed`.

Это полигон для дефекта D7 SUBAGENT-CARD-SHRED (шред полей заголовка до
`haik`/`runni`/`ng` и пустые waterfall-рамки `│ │ │`; реестр
`reports/statusbar-fix-20260919/USER-BUGS-REGISTRY.md`, A8). E2E-покрытие —
termseer-сьют `tests/golden-tui/e2e-patches.yaml` (тест `turn_waves`,
детекторы `d7_subagent_card` / `d7_waterfall_empty`).

Ручная проверка в dsh (сервер уже запущен, провайдер fake):

```
SCENARIO:waves запусти волну
```

## Формат сценария

Файлы `scenarios/*.json`; имя файла без расширения = имя сценария (если `name`
не задан явно). Несколько сегментов одного ответа склеиваются, пока не встретится
`tool_use` (ответ завершается `stop_reason: "tool_use"`) или сценарий не кончится
(`stop_reason: "end_turn"`).

```jsonc
{
  "name": "example",
  "description": "необязательное описание",
  "usage": {
    "input_tokens": 850,                // message_start + message_delta
    "output_tokens": 220,
    "cache_read_input_tokens": 0,
    "cache_creation_input_tokens": 0
  },
  "segments": [
    { "thinking": ["кусок 1", "кусок 2"] },          // thinking-блок
    { "text": ["абзац 1", "абзац 2"] },              // текстовый блок
    { "text": ["..."], "repeatMs": "STREAM_TOTAL_MS" }, // цикл до бюджета времени
    { "tool_use": { "name": "Bash", "input": { "command": "ls -la /tmp" } } }
  ]
}
```

- `text` / `thinking` — массив строк; каждая строка режется на куски по `CHUNK_CHARS`,
  между дельтами пауза `DELTA_MS`.
- `repeatMs` — число (мс от начала ответа) или имя env-переменной (строка вида
  `STREAM_TOTAL_MS`); пул кусков циклится, пока не истечёт бюджет. Только для стрима;
  non-stream отдаёт одну итерацию.
- `tool_use.input` — произвольный JSON-объект; сервер стримит его как
  `input_json_delta`. Если в запросе есть `tools`, имя сопоставляется с ними
  (точное совпадение, затем case-insensitive); реального исполнения на сервере нет —
  инструмент исполняет сам dsh в своей песочнице и присылает `tool_result`.

## Диалоговая машина (состояние per-сессия)

- Сессия = отпечаток (sha256) первого пользовательского сообщения. Продолжения
  цикла `tool_use -> tool_result` попадают в ту же сессию.
- После `tool_use` сервер ставит указатель на следующий сегмент и ждёт `tool_result`
  в следующем запросе (последнее сообщение содержит блок `tool_result`), после чего
  продолжает сценарий.
- Если сегментов после `tool_use` нет, continuation отдаёт закрывающий текст
  (пустой ответ harness трактует как `EMPTY_RESPONSE`-ошибку, поэтому этого не допускаем).
- `input_tokens` каждого ответа растёт на 800 за каждый `tool_result` в истории —
  ctx-бар двигается по ходу цикла инструментов.
- Компакция истории в dsh меняет первое сообщение -> новая сессия, сценарий
  начинается заново с `short`.

## Usage и масштабирование

`message_start` несёт полный input-usage (input/cache_read/cache_creation) и стартовый
`output_tokens: 4`; финальный `message_delta` — полный usage сценария. Множитель
`FAKE_USAGE_SCALE` применяется ко всем числам — удобно проверять другие пороги
ctx-бара/comp-поля. Cost при этом остаётся 0: у hand-declared модели нет прайсинга
в каталоге, и pi-ai считает стоимость по каталогу, а не по ответу сервера.

## Env-параметры

| Переменная         | По умолчанию     | Смысл                                          |
|--------------------|------------------|------------------------------------------------|
| `PORT`             | `8787`           | порт сервера                                   |
| `HOST`             | `127.0.0.1`      | адрес привязки                                 |
| `DELTA_MS`         | `25`             | пауза между дельтами (реалистичный tps)        |
| `CHUNK_CHARS`      | `4`              | символов на одну дельту                        |
| `STREAM_TOTAL_MS`  | `150000`         | бюджет сценария `long` (2.5 мин; держите ниже `streamIdleTimeoutMs` роута, по умолчанию 5 мин) |
| `FAKE_USAGE_SCALE` | `1`              | множитель usage-чисел сценария                 |

| `MAX_SESSIONS`     | `512`            | лимит сессий диалога (LRU-вытеснение)          |
| `SESSION_TTL_MS`   | `7200000`        | TTL неактивной сессии (2 ч)                    |

## Логи

Каждая пара запрос/ответ — одна строка JSONL в `logs/server-YYYYMMDD.jsonl`
(`ts`, `session`, `scenario`, `marker`, `segments_done`, `segments_total`, `stream`,
`stop_reason`, `usage`, `model`, `duration_ms`, `aborted?`). Для отладки и проверок:
`jq . logs/server-*.jsonl | tail`.

## Автопроверка

```bash
node tools/dsh-fake-llm/selftest.mjs
```

Поднимает сервер на случайном порту `127.0.0.1` и прогоняет реальные HTTP-запросы:
(a) non-stream JSON с usage; (б) SSE-последовательность с `message_stop`;
(в) полный цикл `Bash -> Read -> Write` по `tool_result`; (г) health;
(д) ctx90 ~90% окна; (е) длительность `long`; (ж) `waves` — `tool_use
subagent` с валидным input, continuation по `tool_result` и дефолтный
`short` для запроса без маркера; (з)–(м) двойные волны субагентов, точный
usage, delayMs/thinking, repeatMs-компакция, авто-continue после max_tokens
через runtime-context-снимок; (н) реплей — конвертация мини-сессии в
replay-сценарий (`--speed 0.5 --max-delay 40`) и сквозной прогон на вложенном
сервере: дельты совпадают с исходным ходом, межчанковые паузы — с таймингами
записи, ходы end_turn / tool_use / max_tokens CUT + хвост. Выход:
`PASSED/FAILED` по пунктам (`SELFTEST PASSED: 13/13`), exit code 0 только
если всё прошло.

## Реплей реальных сессий

Scripted-сценарии выше задают тайминги глобально (`DELTA_MS`/`CHUNK_CHARS`), а
реальная модель дышит неравномерно: burst-пачки чанков сменяются секундными
затишьями. Таймингово-зависимые дефекты TUI (мигание рамки, дрожь рядов, щели
под статус-баром) на scripted-сценариях не воспроизводятся — реплей лога
реальной сессии единственный способ поймать их на стенде. Конвертер превращает
`session.jsonl` (персистентный журнал агента dsh) в сценарий fake-llm с
точными межчанковыми паузами записи.

Конвейер:

1. Взять лог сессии dsh: `session.jsonl` или сжатый `session.jsonl.zstd`.
2. Прогнать конвертер — JSON-сценарий ложится в `scenarios/`.
3. Перезапустить сервер (набор сценариев фиксируется на процесс), в dsh
   отправить сообщение с маркером `SCENARIO:<name>`.
4. Сервер подаёт N-й записанный ход по N-му маркерному сообщению сессии:
   первое маркерное (интент юзера) — ход 1, каждый следующий
   `tool_result`/continuation — следующий ход; сообщения без маркера получают
   дефолтный `short`. Циклы `tool_use` и обрывы `max_tokens` доигрываются
   штатной continuation-машиной.

### Конвертер session-to-replay.mjs

```bash
node tools/dsh-fake-llm/session-to-replay.mjs <session.jsonl[.zstd]> [опции]
```

| Опция         | Default         | Смысл                                                                    |
|---------------|-----------------|--------------------------------------------------------------------------|
| (позиционный) | —               | путь к логу; `.zst`/`.zstd` распаковывается `zstdcat` (мультифрейм нативно, нужен zstd в PATH) |
| `--name`      | `replay-<sid8>` | имя сценария = маркер `SCENARIO:<name>` (первые 8 символов id сессии)    |
| `--speed`     | `1`             | множитель пауз: `0.5` = вдвое быстрее записи, `2` = вдвое медленнее      |
| `--turns`     | все             | номера ходов через запятую и диапазонами: `1,3,5-7`                       |
| `--max-delay` | без потолка     | потолок одной паузы в мс — против «заморозок» реплея на сетевых паузах записи |
| `--out`       | stdout          | файл результата; сводка и предупреждения всегда пишутся в stderr          |

Примеры:

```bash
# ходы 1-3 из zstd-лога, тайминги как записано
node tools/dsh-fake-llm/session-to-replay.mjs \
  ~/.dsh/sessions/<slug>/<id>/session.jsonl.zstd --turns 1-3

# вдвое быстрее, паузы не длиннее 40 мс, сразу в scenarios/
node tools/dsh-fake-llm/session-to-replay.mjs session.jsonl.zstd \
  --speed 0.5 --max-delay 40 --out scenarios/replay-stall.json
```

Сводка в stderr: число ходов/блоков/чанков, статистика пауз (min / медиана /
средняя / max в мс), количество предупреждений.

### Формат replay-сценария

Обычный JSON сценария с корневым полем `replay`:

```jsonc
{
  "name": "replay-ab12cd34",
  "replay": {
    "kind": "session-replay",
    "source": "/abs/path/session.jsonl.zstd",
    "turns": [
      {
        "turn": 1,
        "userText": "текст интента пользователя",
        "delayMs": 5592,   // пауза до первого события хода («модель думает»)
        "usage": { "input_tokens": 850, "output_tokens": 1234 }, // usage шага из лога
        "segments": [
          { "thinking": [ { "text": "кусок", "afterMs": 3 } ] },
          { "text":    [ { "text": "кусок", "afterMs": 25 } ] },
          { "tool_use": { "name": "run_code", "id": "toolu_01...", "input": { "code": "..." },
                          "jsonPieces": ["{\"co", "de\":", " 1}"],  // куски аргументов, как резал стрим
                          "afterMs": [12, 9, 5] } }                 // паузы после каждого куска
        ]
      }
    ]
  }
}
```

Семантика таймингов:

- `delayMs` хода = (первый чанк первого блока − step/start) × `--speed` — окно
  «модель думает» до начала стрима;
- `afterMs[i]` = пауза ПОСЛЕ i-го чанка до следующего (× `--speed`, кламп
  `--max-delay`); у `tool_use` массив параллелен `jsonPieces`;
- `jsonPieces` — куски аргументов tool-call в нарезке записи; их конкатенация
  обязана парситься в JSON-объект (проверяется при загрузке сценария), сервер
  стримит их как `input_json_delta`;
- сегмент может нести `stopReason: "max_tokens"` (CUT-сегмент) — авто-continue
  доигрывает хвост;
- межшаговые паузы (исполнение тулзы, латентность авто-continue) НЕ
  переносятся — они клиентские и в реплее рождаются заново.

### Предупреждения конвертера

На «рваных» логах конвертер не падает — печатает предупреждение в stderr и
восстанавливает ход:

| Предупреждение                                                    | Что значит                                                                                                                                     |
|-------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| `чанки tool-call != аргументам block-end`                          | текст кусков стрима не совпал с полными аргументами block-end (лог потерял/задвоил часть чанков); за основу берутся аргументы block-end         |
| `стрим tool-call обрезан — куски пересобраны из block-end (N шт.)` | конкатенация кусков не парсится в JSON (обрыв записи посреди tool-call); куски пересобраны пропорциональным resplit'ом из block-end.arguments — число кусков сохранено, `afterMs` ложатся 1:1 |
| `куски tool-call без валидного JSON — '{}'`                        | валидного JSON нет ни в кусках, ни в block-end; сегмент получает один кусок `{}`                                                                 |
| `аргументы tool-call не парсятся — input={}`                       | аргументы block-end не JSON — `input` подменён на `{}`                                                                                           |
| `неизвестный finish kind "X" — трактован как stop`                 | стоп-причина шага вне stop/tool-calls/max-tokens (например `error`); трактуется как end_turn                                                      |
| `N чанков вне границ блоков — пропущены`                           | чанки без block-start/block-end (обычно хвост оборванной сессии) — выброшены                                                                     |

Живой пример конвертации реальной сессии (SushiLover, ход 1: 2 сегмента,
32728 чанков, delayMs 5592, tool_use `run_code` из 2632 кусков) — смоук-сэмпл
`reports/w4-evidence/replay-conversion-sample/` (сценарий `sushi-turn1.json` +
лог предупреждений `convert-log.txt`).

## Ограничения

- Cost всегда 0 (см. выше) — сервер не может влиять на цены каталога.
- Сценарий `long`: `STREAM_TOTAL_MS` должен быть меньше `streamIdleTimeoutMs` роута
  (иначе клиент оборвёт стрим по простою, если дельты вдруг остановятся).
- Неизвестное имя в маркере (`SCENARIO:foo`) молча падает в `short`.
- Один сервер = один набор сценариев на процесс; правка JSON требует перезапуска.
